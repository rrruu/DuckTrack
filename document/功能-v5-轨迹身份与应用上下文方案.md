# 功能 v5：轨迹身份与应用上下文方案

> 日期：2026-08-28  
> 状态：**v5-A / v5-B / v5-C 已落地**（2026-08-29）  
> 前置：v1～v4 子任务划分、录制增强、长轨粗切细切已落地  
> 触发：师兄评审指出当前仍是「单条轨迹的通用 GUI 标注器」，与「可训练、可审计的应用级轨迹」存在差距

---

## 1. 背景与问题

### 1.1 现状（v4 及以前）

| 项 | 当前实现 | 问题 |
|---|---|---|
| 顶层 `application` | `platform.node()` → **主机名** | 不能表示用户正在操作的前台应用 |
| 逐步上下文 | 仅有坐标、截图、`monitor_id` | 缺少进程、窗口标题、窗口矩形、DPI、UI Automation |
| `events.jsonl` | 有原始事件流，但无稳定 `event_id` | 调试与审计只能靠时间戳猜 |
| `trajectory[]` | 身份靠**数组下标** | 保存/删步/合并后下标会变，无持久 `step_id` |
| 合并导出 | `type` / `scroll` / `dragTo` / `hotkey` 等为 **N→1** | 导出结果无法列出「由哪些原始事件合成」 |

### 1.2 v5 目标

1. **身份可追溯**：每条原始事件有稳定 `event_id`；每个 trajectory step 有稳定 `step_id`，并记录 `source_event_ids`（及合并规则）。  
2. **应用可识别**：每步（或每个重要事件）附带 **前台应用上下文**（进程、窗口、矩形、DPI）；顶层字段语义纠正。  
3. **向后兼容**：旧字段保留；新字段为**增量**；旧标注页/划分逻辑可忽略新字段继续工作。  
4. **分阶段交付**：先做身份与追溯（v5-A），再做应用上下文（v5-B），UIA/版本信息（v5-C，可选）。

### 1.3 非目标（v5 不做）

- 不做完整「控件级」UI Automation 树默认落盘（体积与隐私问题，留 v5-C 可选）。  
- 不改变 v4 子任务划分算法本身（划分可读新字段，但非必须）。  
- 不强制部署 cloud_server。  
- 不重构标注页 UI（仅保证读旧轨迹不报错）。

## 2. 总体设计

```text
用户输入（pynput）
    │
    ├─ 写入 events.jsonl
    │     每条：event_id + action + 原始参数 + context（v5-B）+ 截图
    │
    └─ 停止录制 → _export_trajectory_json()
            │
            ├─ 合并/合成（type、scroll、dragTo、hotkey …）
            │
            └─ trajectory.json
                  每步：step_id + step_seq + source_event_ids + merge_rule + context
                  顶层：host_name + primary_application（纠正 application 语义）
```

**原则：**

- `event_id` 在 **入队时**分配，写入 `events.jsonl` 后不变。  
- `step_id` 在 **导出为 trajectory step 时**分配，写入 `trajectory.json` 后不变（删步/重排只改 `sub_tasks` 范围，不回收 id）。  
- 1:1 动作（如 `click`）：`source_event_ids` 长度为 1。  
- N:1 合并动作：`source_event_ids` 按**时间顺序**列出全部源事件；`merge_rule` 标明规则名。

## 3. v5-A：事件与步骤身份（优先实现）

### 3.1 `events.jsonl` 新增字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `event_id` | `string` | 是 | 稳定 ID，建议 `evt_<uuid>` 或 `evt_000042`（录制内单调递增亦可，但 UUID 更安全） |
| `event_seq` | `int` | 否 | 录制内从 0 递增序号，便于人类阅读 |

其余字段与现网一致（`time_stamp`, `action`, `x`, `y`, …）。

### 3.2 `trajectory[]` 每步新增字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `step_id` | `string` | 是 | 稳定 ID，建议 `stp_<uuid>` |
| `step_seq` | `int` | 是 | 导出时轨迹内从 0 递增的可读序号（与 `trajectory[]` 下标一致；对应 event 侧 `event_seq`） |
| `source_event_ids` | `string[]` | 是 | 合成该步的全部 `event_id`；1:1 时长度为 1 |
| `merge_rule` | `string` | 否 | 合并规则名；1:1 可为 `direct` 或省略 |
| `source_event_seq` | `int[]` | 否 | 与 `source_event_ids` 对应的 `event_seq`，调试友好 |

**`merge_rule` 枚举（建议）：**

| 值 | 含义 |
|---|---|
| `direct` | 无合并，原始事件 1:1 映射 |
| `type_buffer` | 连续 `key_input` 合并为 `type` |
| `scroll_group` | 短时连续 `scroll` 合并 |
| `drag_compose` | `drag_start` + `drag_move*` + `drag_end` → `dragTo` |
| `hotkey_chord` | 修饰键 + `key_input` / 主键 → `hotkey` |
| `key_down_up` | 单独 `press`/`release` → `keyDown`/`keyUp` |
| `hover_finalize` | 悬停结束时写出 `hover` |
| `terminate_append` | 停止录制追加 |

### 3.3 可选调试产物

`recording/.../provenance.json`（可选，默认生成）：

```json
{
  "schema_version": "provenance-v1",
  "steps": [
    {
      "step_id": "stp_...",
      "step_seq": 0,
      "step_index": 0,
      "merge_rule": "direct",
      "source_event_ids": ["evt_..."]
    }
  ]
}
```

便于不打开巨大 `trajectory.json` 也能做审计（`step_seq` 与 `step_index` 同值；后者为兼容别名）。

## 4. v5-B：应用上下文（第二阶段）

### 4.1 每步 / 每事件 `context` 对象

在 **events.jsonl** 与 **trajectory step** 上均可挂 `context`（导出时从「主源事件」或「最后事件」继承，合并步可挂 `context_at_merge` 或取首事件 context）。

| 字段 | 类型 | v5-B 必填 | 说明 |
|---|---|---|---|
| `process_name` | `string` | 推荐 | 如 `notepad.exe` |
| `process_id` | `int` | 否 | Windows PID |
| `exe_path` | `string` | 否 | 可执行文件完整路径（注意隐私，可 env 关闭） |
| `app_display_name` | `string` | 否 | 文件版本 ProductName（需读 PE） |
| `app_version` | `string` | 否 | 如 `10.0.19041.1` |
| `window_title` | `string` | 推荐 | 前台窗口标题 |
| `window_handle` | `string` | 否 | HWND 十六进制字符串 |
| `window_rect` | `object` | 推荐 | `{left, top, right, bottom}` 屏幕像素 |
| `client_rect` | `object` | 否 | 客户区矩形 |
| `monitor_id` | `string` | 否 | 与 step parameters 中一致 |
| `dpi_scale` | `number` | 否 | 该显示器有效缩放，如 `1.0`、`1.25` |
| `is_elevated` | `boolean` | 否 | 是否提升权限进程 |

**采集时机：** `_enqueue_event` 时或 `_capture_step_artifacts` 前，调用 Windows API 读取**当时前台窗口**（`GetForegroundWindow` 等）。  
**性能：** 仅对 `important=True` 事件采样；`drag_move` 可只记坐标不重复采 context（由 `drag_end` 携带）。

### 4.2 顶层 `trajectory.json` 语义纠正

| 字段 | v4 及以前 | v5 建议 |
|---|---|---|
| `application` | 主机名（误导） | **废弃写入主机名**；改为 `primary_application`（见下） |
| `host_name` | 无 | 原 `application` 语义迁到此字段 |
| `primary_application` | 无 | 整轨「主应用」摘要，如步数最多的 `process_name` |
| `schema_version` | 无 | 如 `ducktrack-trajectory-v5` |

**兼容策略：** v5 仍**可选**在 `application` 写入 `primary_application.process_name`，避免极旧读者崩溃；文档标明 deprecated。

### 4.3 v5-C（可选，已实现）

- UI Automation 快照：`context.uia` 子对象（`control_type`, `automation_id`, `name`, `bounding_rectangle`）。  
- 默认 **关闭**；`DUCKTRACK_UIA=1` 开启；仅对 **click 类**动作（`left_click` / `right_click` / 双击）在 `(x,y)` 处 `ElementFromPoint` 采样。  
- 实现：`ducktrack/uia_context.py`（comtypes + `UIAutomationCore.dll` 薄封装；未启用 OpenAdapt `capture_window_data`）。

## 5. 合并前后对照（摘要）

完整 JSON 见：`document/v5-轨迹字段样例.json`。

| 场景 | events.jsonl（合并前） | trajectory step（合并后） |
|---|---|---|
| 单击 | 1× `left_click` | 1× `click`，`merge_rule=direct` |
| 打字 | N× `key_input` | 1× `type`，`merge_rule=type_buffer` |
| 滚轮 | M× `scroll` | 1× `scroll`，`merge_rule=scroll_group` |
| 拖拽 | `drag_start` + `drag_move*` + `drag_end` | 1× `dragTo`，`merge_rule=drag_compose` |
| 快捷键 | `press`(ctrl) + `key_input` + `release`… | 1× `hotkey`，`merge_rule=hotkey_chord` |

## 6. 环境变量（草案）

| 变量 | 默认 | 说明 |
|---|---|---|
| `DUCKTRACK_EVENT_IDS` | `1` | 是否为 events 写入 `event_id` |
| `DUCKTRACK_STEP_IDS` | `1` | 是否为 trajectory 写入 `step_id` |
| `DUCKTRACK_PROVENANCE_JSON` | `1` | 是否写出 `provenance.json` |
| `DUCKTRACK_FOREGROUND_CONTEXT` | `1` | 是否采集前台窗口上下文 |
| `DUCKTRACK_CONTEXT_EXE_PATH` | `0` | 是否写入完整 `exe_path` |
| `DUCKTRACK_UIA` | `0` | 是否采集 UI Automation（v5-C） |

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 前台窗口采集增加延迟 | 仅 important 事件；drag_move 跳过 |
| `exe_path` 泄露路径 | 默认不写，env 开启 |
| UIA 体积过大 | v5-C 默认关；仅 click 采样 |
| 旧脚本读 `application` 当应用名 | 过渡期双写 + 文档 deprecated |
| 删步后数组下标 / `step_seq` 可能变但 `step_id` 不变 | 子任务仍用 `start_step`/`end_step` 下标（与导出时 `step_seq` 对齐）；`step_id` 仅用于审计 |
